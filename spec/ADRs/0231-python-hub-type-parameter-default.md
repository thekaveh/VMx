# ADR 0231 — Python hub type parameters default to `Message`

- **Status:** Accepted
- **Date:** 2026-11-15 (decision 12 revised 2026-11-22, when the owner accepted the source break)
- **Spec version:** 3.30.0 (Python flavor and ADR registry only; no spec chapter or conformance ID change; one HISTORY citation, decision 11)
- **Clarifies:** [ADR-0009](0009-cross-flavor-divergence-catalogue.md) (§2, the `MessageHub` parameterisation row). Related: #1903 (the issue this ADR implements), #1582 (a typed stream of one application message type, a separate change to the same hub).

## 1. Context

`MessageHub` is generic over `_THubMessage`, a type variable with a bound and no default. `MessageHubProto` and `TransactionalMessageHubProto` are generic over `TMessage`, which has the same shape. Under `mypy --strict`, a bare `hub = MessageHub()` needs an annotation (`var-annotated`), and a bare `MessageHub` parameter is an error (`type-arg`). Consumers therefore write `MessageHub[Message]` on most hub declarations.

Only `MessageHub.send` uses the type variable. `MessageHub.messages` and the protocol `messages` property are typed `Observable[Message]` for every parameterisation, so `Message` is the parameter that consumers use.

ADR-0009 records the class-generic `MessageHub[Message]` shape as the idiomatic Python form. It does not discuss a default.

PEP 696 type parameter defaults let a bare generic mean `Generic[Default]`. `typing.TypeVar` accepts `default=` only from Python 3.13, and the package supports 3.10 to 3.14. `typing_extensions.TypeVar` accepts `default=` from typing-extensions 4.4.0, but the release note alone does not set the floor, because the 4.4.0 class fails at import on Python 3.12 and later. The checks below ran in scratch virtual environments, with the `vmx` source on the path. Each check imports `vmx` and reads `__default__` of both type variables.

- **Python 3.10.** typing-extensions 4.4.0 with reactivex 4.1.0 imports `vmx`, and both defaults resolve to `Message` (checked 2026-11-22). With typing-extensions 4.12.0 the full test suite passes (2467 tests, 2026-11-15). The suite cannot start at 4.4.0, because the test tooling (`pytest-asyncio`) needs a newer typing-extensions, so 4.4.0 was checked with the import probe only.
- **Python 3.12.** typing-extensions 4.4.0 and 4.5.0 fail at `import typing_extensions` (`TypeError: type 'typing.TypeVar' is not an acceptable base type`), before `vmx` is imported (checked 2026-11-22). 4.10.0, 4.11.0 and 4.12.0 pass the probe.
- **Python 3.13 and 3.14.** typing-extensions 4.4.0 and 4.5.0 fail at import with the same `TypeError`. Releases 4.6.0, 4.8.0, 4.10.0 and 4.11.0 import, but creating a defaulted type variable fails (`AttributeError: attribute '__default__' ... is not writable`) on both versions (checked 2026-11-22). Releases 4.6.0 to 4.11.0 were checked on 3.13 on 2026-11-15 and fail the same way. Typing-extensions 4.12.0 passes the probe on both versions, and both defaults resolve to `Message` for `vmx`.
- At runtime `vmx` imports only `TypeVar` from typing-extensions. `assert_type` appears only in the mypy test file, which pytest does not run.
- `reactivex` 5.1.0, the release the lock resolves, requires `typing-extensions>=4.15.0`. The floor in this ADR therefore matters when a resolver selects a `reactivex` 4.x release, which `vmx` allows (`reactivex>=4.0.4`).
- `vmx` does not pin the copy of typing-extensions that `reactivex` brings, so that copy may be any release, including the releases that fail on Python 3.12 and later.

## 2. Decision

1. **Default on the hub type variable.** `_THubMessage` is declared with `bound=Message, default=Message`, so a bare `MessageHub` means `MessageHub[Message]`. Reason: a bare form then means the parameterisation that consumers already write, and no consumer changes its code.
1. **One declaration for every Python version.** `_THubMessage` and `TMessage` import `TypeVar` from `typing_extensions` on Python 3.10 to 3.14, not from `typing`. Reason: a single declaration covers every version. The alternative, a version-conditional choice between `typing.TypeVar` and `typing_extensions.TypeVar`, needs two declarations for one contract and a conditional dependency. The simplest rule that is uniform is the single declaration.
1. **Explicit dependency with a floor of 4.12.0.** `langs/python/pyproject.toml` declares `typing-extensions>=4.12.0` in `[project] dependencies`. This is a new explicit runtime dependency. Before this change the package declared no typing-extensions dependency and used the copy that `reactivex` brings. The floor is the lowest release, among the releases checked in section 1, that passes the import probe on every supported Python version (3.10 to 3.14). Releases 4.4.0 and 4.5.0 fail at `import typing_extensions` on Python 3.12, 3.13 and 3.14, so a floor of 4.4.0 would admit an import failure on those versions. Releases 4.6.0 to 4.11.0 fail on Python 3.13 and 3.14. On Python 3.10 to 3.12, releases from 4.10.0 also pass the probe, so the floor is higher than those versions need. The single floor is kept for decision 2's single declaration and one rule for every version (section 4).
1. **Same default on the protocols.** `TMessage`, the type variable of `MessageHubProto` and `TransactionalMessageHubProto`, has `default=Message` as well. It stays contravariant. Reason: one rule for every hub type variable. A bare `MessageHubProto` annotation then means `MessageHubProto[Message]`, the same as the hub. The protocols use the same bound, and `Message` is the parameter that consumers use.
1. **A typing contract, checked by mypy.** `langs/python/tests/typing/message_hub_default.py` asserts the bare forms with `typing_extensions.assert_type`. `.github/workflows/python.yml` runs `mypy --strict` on it in a step after the `Mypy` step. Reason: a default is a static property. pytest does not collect the file, because its name is not `test_*.py`, and the public API baseline does not render a bare annotation. The mypy step is the only check that fails when the default is removed. Verified 2026-11-15: removing the hub default, removing the protocol default, or setting the hub default to `Any` each makes `mypy --strict` fail on this file.
1. **Public API baseline unchanged.** `langs/python/api/vmx.api.txt` has no diff on Python 3.12. The base of `MessageHub` still renders `typing.Generic[~_THubMessage]`, and the protocol bases still render with their type variables. The baseline therefore does not guard the default, and decision 5 does.
1. **Runtime behavior unchanged.** `MessageHub` and the protocols change only in their type variables. Explicit parameterisations such as `MessageHub[Message]` keep their meaning. Existing annotations in the docs and the examples remain valid.
1. **ADR-0009 updated in place.** The `MessageHub` parameterisation row now says that a bare `MessageHub` means `MessageHub[Message]`, and it links to this ADR. The row's Status line reads `clarified by ADR-0120, ADR-0121, ADR-0231`, and its registry cell reads `clarified by 0120, 0121, 0231`. Both use the list form that ADR-0009 already carried, with ADR-0231 added, as ADR README section 2.3 requires. ADR-0009 gains no other text. Reason: the row is the cross-flavor record of this shape, and this ADR holds the reasons for the change and for the source break.
1. **No conformance ID, spec chapter or version change in this pull request.** No `spec/NN-*.md` chapter changes, and no package version changes. The source version stays 3.30.0. The next Python release is a major version (decision 12), and its number is set at release time. The one `spec/HISTORY.md` change is the citation range in section 39 (`ADR-0184 through ADR-0232`), which names this ADR. Reason: `tools/tests/test_adr_release_records.py` (rule B) requires every ADR labelled with a release to be cited in that release's HISTORY section, and this ADR is labelled 3.30.0.
1. **Locks record the new dependency.** `langs/python/uv.lock` and four example locks (`examples/python`, `examples/python/textual/inspector`, `examples/python/textual/notes_showcase` and `examples/python/nicegui/notes_showcase`) record the `vmx` dependency on `typing-extensions` with the `>=4.12.0` specifier. Reason: each example installs `vmx` by path and records its dependency list, and `uv lock --locked` fails until the lock is updated. No pinned package version changes.
1. **CHANGELOG.** `langs/python/CHANGELOG.md` records the change under `### Changed` in the `[3.30.0] — unreleased source version` section (CONTRIBUTING section 4.3). The entry starts with `**BREAKING:**`, describes the behavior change, gives the migration, and states that the next Python release is a major version.
1. **Source break, accepted by the owner, under README section 6.1.** The plain-mypy and strict-suppression changes in section 3 are a source break for the Python flavor. Code that type-checked before the change now fails to type-check. Only a bare `MessageHub`, `MessageHubProto` or `TransactionalMessageHubProto` annotation changes outcome, and only under plain mypy or under a suppressed `type-arg` error in strict mypy. Runtime behavior and every explicit parameterisation are unchanged. The migration is one line, `MessageHub[Any]`, for code that needs the old acceptance. The owner accepted this source break on 2026-11-22 (option A). The next Python release is therefore a major version, and the number is set at release time by the owner. This pull request makes no version bump. The CHANGELOG lists the change as `**BREAKING:**`.

## 3. Consequences

- **Classification.** A source break under README section 6.1. The owner accepted it on 2026-11-22, so the next Python release is a major version (decision 12). It is not a runtime change.
- Under `mypy --strict`, a bare `MessageHub()`, a bare `MessageHub` parameter and a bare `MessageHubProto` or `TransactionalMessageHubProto` annotation type-check as `Message` parameterisations. Consumers can drop the annotation.
- Under plain mypy (without `disallow_any_generics`), a bare annotation used to mean `Any` and accepted a hub of any message type. It now means `Message`. A parameter annotated bare rejects `MessageHub[MyMessage]` or a `MessageHubProto[MyMessage]` hub, and mypy reports `arg-type`. Verified 2026-11-15. The fix for such code is an explicit parameterisation, such as `MessageHub[Any]` or `MessageHub[MyMessage]`.
- Under plain mypy, a bare `MessageHub()` assigned to an unannotated variable was already `var-annotated`. It now type-checks as `MessageHub[Message]`, and passing that variable where a `MessageHub[MyMessage]` is expected, or sending a non-`Message` to it (`hub.send("text")`), is an error. Verified 2026-11-15 on develop and on the PR head.
- Under `mypy --strict`, a bare annotation was already an error (`type-arg`), so most strict code sees no change. Two kinds of strict code do see it:
  - A bare parameter whose `type-arg` error was suppressed with `# type: ignore[type-arg]` now means `MessageHub[Message]`, and a hub of another message type is an `arg-type` error. The repository's `tests/unit/messages/test_property_value_changed.py` was such a case. It now annotates `MessageHub[PropertyChangedMessage[_TestSource]]` and no longer suppresses the error.
  - An unannotated `hub = MessageHub()` infers `MessageHub[Message]` instead of `MessageHub[Any]`, and `var-annotated` is gone. Sending a non-`Message` to it is an `arg-type` error, as in the plain-mypy case above.
  - Measured 2026-11-15 with `mypy --strict tests` (the `tests/` tree, which CI does not check under strict): 1295 errors on develop and 1410 on the PR head. 120 lines are new and 5 are gone. No new error is in `src/vmx` or `tests/typing`, which stay strict-clean. 119 of the 120 new lines mention an existing `MessageHub[object]` annotation, and every file that gains one already has a `type-var` error for that annotation on develop. The remaining new line is the `send` case above.
- The Python package declares `typing-extensions>=4.12.0` as a new runtime dependency. Installing `vmx` upgrades a typing-extensions older than 4.12.0, and installs one where none is present.
- Each Python CI matrix cell runs one more `mypy --strict` step.
- The Swift and Rust hubs and the C# and TypeScript shapes are unchanged. The bare form exists only in Python, as ADR-0009 records.

## 4. Rejected alternatives

- **`typing.TypeVar` on Python 3.13 and later, `typing_extensions.TypeVar` below 3.13.** Two declarations for one contract, plus a conditional dependency marker. Rejected in favor of decision 2.
- **The issue's proposed floor, `typing-extensions>=4.4.0`.** Rejected: 4.4.0 and 4.5.0 fail at `import typing_extensions` on Python 3.12, 3.13 and 3.14, and 4.6.0 to 4.11.0 fail when a defaulted type variable is created on Python 3.13 and 3.14 (section 1). A floor of 4.4.0 would let a resolver install a version that breaks `import vmx` on those versions. The 3.12 import failure was reproduced again on 2026-11-22 with Python 3.12.9. Issue #1903 names the 4.4.0 floor in its Proposed approach, step 2. This decision supersedes that text, and the owner amends the issue to match.
- **A floor that depends on the Python version, such as 4.4.0 below 3.12 and 4.12.0 from 3.12 up.** Rejected: the lower floor saves little, because `reactivex` 5.1.0 requires typing-extensions 4.15.0, and it adds a second floor to keep correct. The single floor of 4.12.0 is the simplest rule that passes on every supported version.
- **The transitive copy from `reactivex`.** Rejected: `vmx` does not pin that copy, so it may be any release, including the releases that fail on Python 3.12 and later.
- **`default=Any` or `default=object`.** Rejected: the bare forms would mean `MessageHub[Any]` or `MessageHub[object]`, not `Message`. The `Any` default fails the typing contract (decision 5, verified 2026-11-15).
- **Editing ADR-0009 alone, with no new ADR.** Issue #1903 proposed this. Rejected as the only record: the reasons for the default, the floor and the protocol choice need an ADR that ADR-0009 can link to. ADR-0009 keeps the row and gains the back-link.
- **Calling the change typing-only, with no source break.** Rejected. README section 6.1 and the ADR-0009 precedent count a compile-time rejection of code that compiled before as a source break. The policy has no exemption for typing changes.
- **A narrow 3.x minor-version exception for this break.** Rejected by the owner's decision of 2026-11-22 (option A): the source break is accepted as a source break, and the next Python release is a major version.
- **Bumping the Python version in this pull request.** Not taken. A version bump is an owner release action. The next Python release is a major version, and the owner sets its number at release time (decision 12).
