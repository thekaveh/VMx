# ADR 0257 — A notification's timer and decay-tick failures never reach the scheduler

- **Status:** Accepted
- **Date:** 2026-11-26
- **Spec version:** 3.30.0 (chapter 16 §6, a new paragraph; chapter 16 §9; chapter 12 `NOTIF-021`; `NOTIF-019` and `NOTIF-020` are unchanged)
- **Extends:** [ADR-0191](0191-subscriber-failures-do-not-stop-delivery-or-detach.md) (adds the `NotificationVM` timer deliveries to the stream-fed route and keeps its rules). Related: [ADR-0197](0197-notification-state-stops-at-resolution-and-hub-dispose.md) (render state after resolution), [ADR-0219](0219-scheduler-contract-delayed-task-and-rust-timers.md) (§2.4, the `DelayedTask` failure route), issue #1875.

## 1. Context

`NotificationVM` (chapter 16 §6) arms two actions on the injected scheduler. The lifespan timer auto-dismisses the notification when it expires. With a `tickInterval`, a decay tick raises `PropertyChanged` for `RemainingTime` and `Opacity`, then reschedules.

Neither action had an exception boundary in C#. Auto-dismiss resolves through `hub.Resolve`, and `Dismiss` raised the `IsResolved` change only after that call returned. A `Pending` subscriber that throws in that call therefore ended the action before the change was raised. A `PropertyChanged` handler that throws ended a decay tick before it rescheduled. On `DefaultScheduler.Instance`, the real-time scheduler of chapter 11 §6.1, the failure is unhandled on a timer thread, and .NET ends the process. Under a test scheduler, the failure surfaces in the code that advances the clock, and the `IsResolved` change is missing.

Chapter 03 §3.6 defines the failure routes of the library's delivery channels. It states that it does not cover other `PropertyChanged` handlers, and it does not name the `NotificationVM` timer path. A debounce timer and a failing `DelayedTask` action are stream-fed (ADR-0219 §2.4). The timer path of `NotificationVM` is the same kind of delivery: the scheduler, not the caller, runs it.

## 2. Decision

1. **The timer path is stream-fed.** A failure raised by a `Pending` subscriber or a `PropertyChanged` handler during auto-dismiss, or during a decay tick, follows the stream-fed route of chapter 03 §3.6. It never reaches the scheduler. The route is flavor-specific: C# discards it, as `DelayedTask` does (ADR-0219); Python logs it with `logger.exception`; TypeScript reports it through rxjs `config.onUnhandledError` (with no handler set, rxjs rethrows it on a timer; see Consequences); Rust catches it. Swift needs no containment at expiry, because its subscribers cannot throw. Its test is a regression test of the timeline.
1. **The VM-level containment is the default expiry hook.** The containment is the default body of the expiry hook (`OnExpire` in C#, `_on_expire` in Python, `onExpire` in TypeScript). It covers the default auto-dismiss only. An override of the hook is not contained: a failure that it raises reaches the scheduler, as it did before this ADR.
1. **State first, and the change is always raised.** Auto-dismiss and `DismissCommand`, through the same `Dismiss` path, commit the resolved state before the hub call. They raise the `IsResolved` change, then `RemainingTime` and `Opacity`, even when `hub.resolve` throws. A `DismissCommand` hub failure keeps the route that its flavor gives a command call. `ResolveWith`, which the `ConfirmationVM` approve and reject commands call, keeps its current order.
1. **The decay tick, per flavor.** In C# and Python, the tick raises each change under its own VM-level containment (`RunTimerAction` in C#, `_raise_contained` in Python) and then reschedules while `RemainingTime` is positive, so one failing handler does not stop the decay. In TypeScript the VM has no containment on the decay tick. Subscriber and handler isolation comes from rxjs, which keeps the subject delivering and reports a failing handler through `config.onUnhandledError` (or rethrows it on a timer when no handler is set; see Consequences). The tick reschedules as that isolation allows, and the VM adds no containment there. Swift's subscribers cannot throw, so its tick needs no containment. Rust has no decay tick.
1. **The rule is one conformance ID.** `NOTIF-021` tests the timeline in each flavor (§9 of chapter 16 maps it to §6). The override test of each of C#, Python and TypeScript carries the marker. Rust and Swift have no override test: Rust has no subclassable expiry hook, and Swift's hook cannot throw. A flavor whose subscribers cannot throw (Swift) asserts the same timeline with no failing subscriber or handler. Rust has no `IsResolved` change event and no decay tick, so its test asserts the expiry timeline with a panicking Pending subscriber.
1. **Versions and records.** `spec/VERSION` stays at 3.30.0, because no `spec-v3.30.0` tag exists, as ADR-0214 to ADR-0255 did. No public member changes, so the API listings do not change. Each changed package records the fix in its CHANGELOG under its current unreleased source version.

## 3. Consequences

- A `Pending` subscriber or a `PropertyChanged` handler that fails at expiry or during a tick no longer stops the process on `DefaultScheduler.Instance`, and no longer hides the `IsResolved` change under a test scheduler.
- A failure is discarded silently in C# and Rust, as the stream-fed route already does for other deliveries. Python logs it. TypeScript follows the pre-existing route described below. A diagnostic of a failing handler therefore depends on the flavor.
- Other handlers of the same `PropertyChanged` invocation may still be skipped when one throws, because the change notifications are not fanned out. Chapter 03 §3.6 does not cover these handlers, and this ADR does not change that.
- `ConfirmationVM` keeps its no-op auto-dismiss. Its decay tick changes only where the flavor contains the tick (C# and Python).
- An override of the expiry hook is not contained. C#, Python and TypeScript each have a test for this, and each test carries the `NOTIF-021` marker.
- A handler that throws on the `IsResolved` change at auto-dismiss is tested in C#, Python and TypeScript under the `NOTIF-021` marker. The TypeScript test is routed to rxjs before the VM containment is reached, so it does not guard the default containment. The TypeScript default containment is pinned only by the hub-resolve test, which makes the hub's `resolve` throw at auto-dismiss. Rust has no such change event, and Swift's subscribers cannot throw.
- Known residual, not fixed here, in C# and Python. A `PropertyChanged` handler that throws on the `IsResolved` change during a `DismissCommand` whose `hub.resolve` also throws replaces the hub's failure for that caller, because the exception of a `finally` block takes the place of the one before it. The caller sees the handler's error and not the hub's. The state is committed, and `hub.resolve` throws as before. The same handler also skips the `RemainingTime` and `Opacity` changes of that resolution: C# raises only `IsResolved` (by source, and by a scratch console probe run against the library), and Python raises only `is_resolved` (by a temporary test). A fix must choose which failure the caller sees, and this ADR does not make that choice. TypeScript has no such residual. A temporary test (not kept) showed that the caller gets the hub's error, that all three changes are raised (`isResolved`, `remainingMs`, `opacity`), and that the handler's error goes to rxjs's unhandled-error route.
- Pre-existing TypeScript route, unchanged by this ADR. With no `config.onUnhandledError` set, rxjs `reportUnhandledError` rethrows the error inside a timer callback. An uncaught exception there ends a plain Node process. ADR-0200 names `config.onUnhandledError` as the route for failures that a flush reports. So a TypeScript subscriber or handler failure at expiry or on a decay tick still ends a plain Node process when no handler is configured. This PR does not change that route.
- Rust's expiry test documents the timeline. It cannot tell which catch contains a panicking Pending subscriber, because the expiry step also runs under `DelayedTaskInner::run`'s `catch_unwind`. The Rust drop and publication tests (`drop_panic_publication.rs`, and the notification dispose tests) exercise the publication path. No `NOTIF-021` test isolates one Rust containment site.

## 4. Rejected alternatives

- **Leave the failure to the scheduler's unhandled path.** That is the current behavior. It ends a C# process on `DefaultScheduler.Instance` and skips the `IsResolved` change under a test scheduler.
- **Wrap the whole decay tick in one boundary.** A single failure would then skip the reschedule and stop the decay. Each change needs its own containment.
- **Route the failure to a caller.** A timer action has no caller. The scheduler thread is the only place the failure can go, so it is contained there.
- **Roll back `IsResolved` when the hub resolve fails.** The hub has already completed the waiter, so the notification is no longer pending. Rolling back would report an open notification that the hub no longer holds.
