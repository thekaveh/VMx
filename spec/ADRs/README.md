# spec/ADRs/

Architecture Decision Records (ADRs) for the VMx spec. Each ADR is a small,
self-contained markdown file numbered `NNNN-kebab-title.md`.

ADRs capture the *why* behind every normative spec change. Per the spec
discipline rule (CONTRIBUTING §3), any modification to a `spec/NN-*.md`
chapter requires a new ADR in the same PR. Exempt paths — `spec/README.md`,
`spec/VERSION`, `spec/HISTORY.md`, `spec/ADRs/**`, `spec/fixtures/**`,
`spec/proposals/**`, and `spec/12-conformance.md` — are enforced by
`.github/workflows/spec-discipline.yml`; typo-only chapter changes can be
waived by a maintainer via the `no-adr-needed` label.

### 1.1 Consolidation opportunities (informative — VMX-120)

The ledger has grown a few near-duplicate clusters. These are recorded here
rather than retro-merged, because every ADR number is referenced from spec
chapters, code comments, and prior PRs and must remain a stable anchor:

- **0020 / 0021** — editorial-only siblings that could be one ADR.
- **0044 / 0045 / 0046** — the three consecutive-day "v2.6 spec-accuracy
  clarification" ADRs share an identical template and split only by chapter;
  a single "v2.6 spec-accuracy" ADR would have sufficed.
- **0039 / 0040 / 0041** — the teaching ADRs. Note **0041 is a KEEP**
  (single-disposable-lifecycle is a live normative decision, not a "rejected
  alternative" write-up like 0039/0040).

Any future consolidation must keep a forwarding stub at each retired number.

## 2. Format

### 2.1 Preamble

Each ADR starts with a title and a bulleted preamble:

```markdown
# ADR NNNN — Short title

- **Status:** Accepted
- **Date:** YYYY-MM-DD
- **Spec version:** X.Y.Z (chapter NN §N, `XXX-NNN`)
- **Extends:** [ADR-NNNN](NNNN-kebab-title.md). Related:
  [ADR-NNNN](NNNN-kebab-title.md), #NNN.

## 1. Context
...

## 2. Decision
...

## 3. Consequences
...

## 4. Rejected alternatives (optional)
...
```

ADR-0128 and later use this form, except ADR-0131. The earlier ADRs and
ADR-0131 use an older form without bullets and without a `Date` field. Its
two lines are `**Status:** Accepted (YYYY-MM-DD)` and
`**Spec version:** introduced in X.Y.Z`.

Both forms stay valid, and tooling reads the `Status` field of both. The body
is hierarchically numbered, as elsewhere in the spec.

### 2.2 Relationship fields

A relationship field names an earlier ADR that this ADR changes:

| Field        | Meaning                                                          |
| ------------ | ---------------------------------------------------------------- |
| `Supersedes` | This ADR replaces the earlier decision, or the named part of it. |
| `Amends`     | This ADR changes a rule of the earlier decision.                 |
| `Extends`    | This ADR adds rules to the earlier decision and keeps its rules. |
| `Clarifies`  | This ADR makes the earlier decision precise without changing it. |

A relationship field can name a part of the earlier ADR, such as "Decision
rule 4" or "§2". `Related:` text after a relationship field, or a `Related`
field of its own, lists other references: ADRs, issues and pull requests.
`Related` creates no relationship.

### 2.3 Status and back-links

The first word of `Status` is `Accepted`, `Superseded`, `Deprecated` or
`Rejected` (VMX-121). Use `Superseded by ADR-NNNN` when a later ADR replaces
the whole decision.

An ADR can name an earlier ADR in a relationship field. The same pull request
then adds a back-link to the `Status` of the earlier ADR and to its registry
`Status` cell. The back-link is `superseded by`, `amended by`, `extended by`
or `clarified by`, followed by the later ADR number.

A back-link can name the affected part, for example
`Accepted (§2.5 amended by ADR-0161)`. `Related` references get no back-link.
Older back-links also use other verbs, such as `corrected by`. The registry
cell repeats the file's back-links without the date.

### 2.4 Numbers

ADR numbers are never reused. ADR-0181, ADR-0182 and ADR-0183 were reserved
for parallel pull requests and never used, so the registry has no rows for
them.
